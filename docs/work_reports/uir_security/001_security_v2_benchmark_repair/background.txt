AntiGravity로 UIR의 Security Extension Task를 수행했었습니다.
그 작업에 대한 문서들은 ./uir/docs/work_reports/000_uir_v2 folder에 있습니다.
이 작업을 검토한 결과, 추가 개발이 필요합니다. 현재 구현 자체는 상당 부분 잘 진행되었지만, 지금 생성된 19,200-case 결과를 SCI 논문의 최종 실험결과로 사용하는 것은 권하지 않습니다.

구현 측면에서는 목표했던 방향이 잘 반영되어 있습니다. UIR-v2는 LLM을 trusted component가 아니라 untrusted transformation component로 두고, UIR를 authoritative Security Reference Representation으로 정의했으며, policy, provenance, capability, data-flow, output guard를 모델 외부에서 강제하도록 설계되어 있습니다. 또한 InputGuard, TrustedEvidenceResolver, ContextFirewall, PolicyEngine, CapabilityGate, OutputGuard, ResourceGuard, Audit까지 원래 작업지시서의 핵심 컴포넌트가 모두 구현된 것으로 보고되어 있습니다.

문제는 evaluation methodology입니다.
	첫째, Full UIR-v2의 실제 machine-readable 결과는 ASR 0%이지만 동시에 FRR 100%, benign utility 0%입니다. 즉 공격 1,400건을 모두 막은 대신 정상 질의 200건도 모두 막았습니다. 이 상태에서는 “안전한 시스템”이라기보다 사실상 fail-closed benchmark configuration에 가깝습니다. Architecture 문서도 이 점을 인정하고 있습니다.

	그런데 별도의 Security Report 마지막에는 benign task utility가 100%이고 zero false reject라고 되어 있습니다. 이는 같은 report 앞부분의 FRR 100%, Utility 0%와 직접 모순됩니다.

	둘째, 더 본질적인 문제는 ASR 판정 방식입니다. GitHub의 실제 evaluation source도 확인했습니다. VanillaSlmBaseline에서는 모델이 실제로 공격 지시를 수행했는지를 분석하지 않고, 해당 case가 adversarial class이면 거의 모두 attack_succeeded=True로 설정합니다. 즉 Vanilla 100% ASR은 실제 모델의 관측 결과라기보다 evaluator 내부 가정입니다.

	반대로 UIR-v2 pipeline에서는 attack_succeeded=False로 초기화한 뒤, ALLOW 경로에서 실제 LLM output이 공격 목적을 달성했는지를 판단하여 True로 바꾸는 로직이 없습니다. 따라서 OutputGuard가 없거나 PolicyEngine이 꺼져 있어도 ASR은 계속 0으로 남을 수 있습니다.

	이 현상은 실제 ablation 결과에서도 그대로 나타납니다. -policy_engine, -context_firewall, -capability_gate, -output_guard, -resource_guard를 제거했는데도 **모든 configuration에서 ASR=0%**입니다. 이것으로는 각 security component가 보안 성능에 기여했다는 논문상의 ablation 주장을 입증할 수 없습니다.

	셋째, benign utility 계산에도 문제가 있습니다. 일부 ablation에서 model output이 schema validation을 통과하지 못해 OutputGuard에서 block되었는데도 policy outcome이 ALLOW라는 이유로 utility가 성공으로 계산되는 경로가 확인됩니다. 따라서 현재 Utility=100%도 “정상 질의에 올바른 답변을 제공했다”는 의미가 아닐 수 있습니다.

	넷째, raw output 안에서 반복적인 ESC control character(\x1b)가 생성된 케이스들도 확인되었습니다. 이는 모델 자체 문제일 수도 있지만 Ollama response decoding, streaming field 처리, concurrency 또는 terminal escape 처리 문제일 수 있으므로, output capture가 정상인지 먼저 확인해야 합니다.

따라서 제 판단은 다음과 같습니다.

Architecture/implementation: 잘 수행됨.
Engineering verification: 상당 부분 성공.
Scientific evaluation: 재설계 필요.
SCI paper Results 작성: 아직 이르며 benchmark v2 재실행 후 진행해야 함.

오히려 좋은 점은, 수정 방향이 명확하다는 것입니다. architecture를 다시 뒤엎을 필요는 없습니다. 현재 UIR-v2 security design은 유지하고 evaluation oracle과 benchmark methodology만 제대로 고치면 됩니다.

특히 새 실험에서는 두 metric을 분리하는 것을 강하게 권합니다.

$$ \text{Model Compromise Rate (MCR)} $$ 와 $$ \text{End-to-End Attack Success Rate (E2E-ASR)} $$ 입니다.

예를 들어 Context Firewall이 없는 상태에서 LLM 자체는 indirect prompt injection에 넘어갈 수 있습니다. 그러나 OutputGuard가 마지막에 이를 막으면:
MCR = 성공
E2E-ASR = 실패
가 됩니다.

이 구분이 바로 HETE의 핵심 철학을 가장 잘 보여줍니다.

HETE의 목표는 LLM이 절대로 공격에 넘어가지 않게 만드는 것이 아니라, 공격에 넘어간 LLM의 출력이 시스템에서 authoritative effect를 갖지 못하게 만드는 것이다.

이것은 단순한 “prompt injection detector” 논문보다 훨씬 강한 Zero-Trust 주장입니다.

또한 현재 architecture에 정의된 10개 invariant 자체는 논문에 사용할 가치가 충분합니다. 예를 들어 user text가 capability를 직접 설정하지 못하게 하고, retrieved content가 intent.action을 변경하지 못하게 하며, untrusted evidence를 authoritative evidence로 사용하지 못하게 하는 규칙들이 명시되어 있습니다. 이 부분은 유지하는 것이 좋습니다.

그래서 이번에는 논문 초안을 만들지 않고, benchmark와 ablation을 SCI 수준으로 수정하기 위한 2차 작업지시서를 작성했습니다.
./uir/docs/work_reports/001_security_benchmark_repair/HETE_UIR_SECURITY_BENCHMARK_REPAIR_WORK_ORDER.md file이 이 2차 작업지시서입니다.

이 작업지시서에는 다음 핵심 수정이 들어 있습니다.
	attack success를 attack-class label이 아니라 실제 observable behavior로 판정
	모든 baseline이 동일한 independent judge를 사용
	benign utility를 ALLOW가 아니라 실제 task correctness로 평가
	trusted evidence가 포함된 정상 질의 fixture 추가
	Model Compromise Rate와 End-to-End ASR 분리
	각 attack class별 구체적인 success oracle 정의
	poisoned RAG에 Retrieval / Admission / Influence metric 분리
	실제 mock tool execution으로 excessive agency 평가
	실제 resource consumption으로 resource attack 평가
	single ablation뿐 아니라 multi-knockout masking study 추가
	report와 JSON 사이 수치 불일치 자동 검증
	ESC/control-character output 문제 조사
	held-out adversarial set 구성
	KO/EN 분리 평가
	반복 run 및 confidence interval/statistical test
	OWASP mapping의 문서 간 ID 불일치 정리

가장 중요한 acceptance condition은 이것입니다.

어떤 component를 제거했을 때 그 component가 담당하는 attack class의 성능이 실제로 악화되어야 한다.

예를 들어:

Full UIR-v2
Indirect Injection E2E-ASR = 0%

-context_firewall
MCR = 65%
E2E-ASR = 8%

-context_firewall -output_guard
MCR = 65%
E2E-ASR = 61%

같은 결과가 나오면 매우 좋은 논문 결과가 됩니다.

이 경우 단순히 “Context Firewall이 필요하다”가 아니라,

Context Firewall은 model compromise를 줄이고, OutputGuard는 compromise가 발생한 경우에도 end-to-end impact를 차단하며 두 계층은 defense-in-depth 관계를 가진다.
라는 훨씬 수준 높은 분석이 가능합니다.

따라서 현재 결과를 폐기할 필요는 없습니다. 현재 19,200-case 결과는 Preliminary Engineering Validation / Benchmark Harness v1로 보존하고, 새 작업지시서대로 evaluator를 고쳐 Benchmark v2를 돌리는 것이 좋습니다. 그 결과가 정상적으로 나오면 그때는 추가 개발보다 SCI 논문 초안 작성으로 바로 넘어가도 될 가능성이 높습니다.
